## 1. Введение и цель документа
Данный документ фиксирует границы (Scope) модуля «Конструктор схем», определяет терминологию, роли пользователей и открытые вопросы, требующие решения до начала проектирования API и базы данных. Документ является отправной точкой для написания User Stories и технического задания.

## 2. Scope (Границы модуля)

### 2.1. Входит в зону ответственности (In Scope)
Модуль представляет собой веб-интерфейс (для десктопа) и серверную логику, позволяющую оцифровывать физическое пространство ресторана.
*   **Управление этажами:** Создание, редактирование названий и удаление этажей.
*   **Управление зонами:** Рисование полигонов (замкнутых областей) для выделения функциональных зон (основной зал, веранда, VIP, бар).
*   **Управление столами:**
    *   Добавление столов на холст.
    *   Настройка свойств: форма (круг, квадрат, прямоугольник), габариты, вместимость (количество посадочных мест).
    *   Манипуляции на холсте: перемещение (drag-and-drop), свободный поворот (0–360°), привязка к координатной сетке.
*   **Версионирование (LayoutRevision):**
    *   Сохранение черновика схемы.
    *   Формирование снимка схемы (JSONB) при публикации.
    *   Просмотр истории ревизий.
    *   Откат (rollback) к любой предыдущей ревизии.
*   **Публикация схемы:** Перевод черновика в статус «Активная» с обязательной валидацией на наличие конфликтов с существующими бронями.

### 2.2. НЕ входит в зону ответственности (Out of Scope)
*   **Гостевой интерфейс:** Выбор стола и бронирование (зона бронирования).
*   **Панель менеджера:** Шахматка, управление бронями, фиксация no-show.
*   **Бэк-офис администратора:** Разграничение прав доступа (RBAC), управление учетными записями (зона Администратора системы).
*   **Интеграции:** Платежные шлюзы, экран кухни (KDS), системы лояльности.
*   **Технологические фичи:** 3D-визуализация залов, AR/VR, поддержка мульти-ресторанности (один инстанс = один ресторан).

## 3. Глоссарий (Domain Model)

| Термин | Определение |
| :--- | :--- |
| **Схема (Layout)** | Совокупность этажей, зон и столов, описывающая физическое пространство ресторана. |
| **LayoutRevision** | Неизменяемый снимок состояния схемы (сериализованный в JSONB), имеющий уникальный ID и временную метку. |
| **Draft (Черновик)** | Текущее состояние схемы, в котором конструктор вносит изменения. Не влияет на процесс бронирования. |
| **Published (Опубликовано)** | Статус ревизии, при котором она становится доступна гостям и менеджерам для бронирования. Может быть только одна активная ревизия в момент времени. |
| **Zone (Зона)** | Многоугольник (полигон) на холсте, определяющий логическую область (например, «У окна»). |
| **Table (Стол)** | Объект на холсте, имеющий координаты (X, Y), геометрию (W, H, Radius), угол поворота и посадочные места. |
| **Soft-lock** | Механизм временной блокировки (TTL 5 минут). Используется для предотвращения одновременного редактирования схемы двумя конструкторами (Optimistic Locking). |
| **Collision (Коллизия)** | Ситуация, когда изменения в схеме (удаление стола, уменьшение мест) ломают уже существующие будущие бронирования. |
| **Grid Snap** | Привязка координат объекта к сетке с заданным шагом для ровной расстановки мебели. |

## 4. Роли и матрица прав (RBAC для конструктора)

| Роль | Права в модуле «Конструктор» |
| :--- | :--- |
| **Конструктор схем** | Создание/редактирование черновика, просмотр истории, публикация схемы (при отсутствии коллизий), откат ревизий. |
| **Администратор системы** | Просмотр всех схем и ревизий, возможность принудительной отмены броней (если конструктор заблокирован), аудит действий. |
| **Менеджер зала (хостес)** | Только чтение (read-only). Видит опубликованную схему для работы с шахматкой. Не может вносить изменения. |

## 5. Бизнес-правила и логика (High-Level)

1.  **Валидация публикации:** При нажатии кнопки «Опубликовать» система должна проверить, не удаляет ли новая ревизия столы, на которые есть активные будущие брони (status = `confirmed`).
    *   *Если конфликт есть:* Публикация блокируется, возвращается ошибка (HTTP 409), пользователю выводится список конфликтных броней.
    *   *Если конфликта нет:* Создается новая `LayoutRevision`, ей присваивается статус `active`, старая ревизия переходит в статус `archived`.
2.  **Механика Soft-lock:** При открытии черновика на редактирование, система «лочит» его за текущим пользователем. Другие пользователи видят сообщение «Схема редактируется другим сотрудником (Имя)». Блокировка снимается по истечении 5 минут бездействия или принудительно.
3.  **Вместимость стола:** Если конструктор уменьшает количество мест стола (например, с 6 до 4), а на этот стол есть бронь на 6 человек, публикация также должна блокироваться с ошибкой валидации.

## 6. Ключевые пользовательские сценарии (Связь с ПЗ №3)

*   **UC-4 (Спроектировать этажи и зоны зала):** Конструктор создает новый этаж, рисует полигон зоны «Летняя веранда», задает ей цветовую маркировку.
*   **UC-5 (Расставить и настроить столы):** Конструктор перетаскивает столы, вращает их, настраивает привязку к сетке.
*   **UC-6 (Опубликовать новую ревизию):** Система проверяет черновик, конструктор вводит комментарий к ревизии («Добавили 3 стола у окна»), система создает снимок JSONB.
*   **UC-7 (Откатить схему к предыдущей ревизии):** Конструктор выбирает из списка ревизию от прошлой пятницы и нажимает «Сделать активной».

## 7. Открытые вопросы (Open Questions)

*Требуют обсуждения с командой и заказчиком.*

1.  **Хранение координат:** Как лучше хранить геометрию? Использовать абсолютные координаты (X, Y в пикселях) или относительные (проценты от ширины/высоты)? *Влияет на адаптивность SVG-холста.*
2.  **Валидация зон:** Должны ли зоны быть строго изолированы (не пересекаться), или стол может стоять на границе двух зон?
3.  **Шаг сетки:** Какой шаг сетки (Grid Snap) оптимален для ресторанных столов — 5px, 10px, 20px?
4.  **Нестандартные формы:** Нужна ли на первом этапе возможность создавать столы произвольной формы (например, буквой «П» или овальные), или достаточно базовых примитивов?
5.  **Откат ревизии:** При откате к старой ревизии, что происходит с бронями, которые были созданы на основе *текущей* (отменяемой) ревизии?
6.  **Массовые операции:** Нужна ли функция «копировать зону со всеми столами» для ускорения оцифровки (например, при создании второго похожего зала)?
